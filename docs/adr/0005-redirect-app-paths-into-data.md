# Redirect paths inside a Port's app into its Data

Some Ports write beside their executable, inside the signed, sandboxed bundle, where the sandbox won't let them write. OpenGOAL's `gk` logs into `data/log` next to it. So the Catalog declares **Redirects**, such as `"redirects": [{ "path": "Contents/Resources/data/log", "to": "Library/Application Support/OpenGOAL/log" }]`: the Packager puts a link at each `path` inside the app that leads, by absolute path, to the folder `to` in the Port's Data. The write lands in the Port's container, where it may write anyway. Frontport creates the folders itself, because a Port like `gk` makes its log folder only when the path looks missing, and through a link that leads nowhere it would try to make it inside its bundle.

## Considered Options

- **Patch the Recipe,** as `opengoal.sh` did. It works, but every Port needs its own patch, kept in step with upstream, and a prebuilt Port has no Recipe.
- **Launch arguments** that point the Port elsewhere. A launch from the Dock or Finder has none, and macOS has no Info.plist key for arguments.
- **A launcher stub** in the app that prepares the folders, then starts the Port. One more program to sign and keep in the sandbox, and upstream's executable no longer starts the app.
- **A writable exception** for the path inside the bundle. The Port could then change its own signed app.

## Consequences

- **The sandbox doesn't widen.** A Redirect leads into the Port's own container, already its writable home, and the sandbox checks where a link leads, so no exception is needed.
- **The folders must exist.** A Redirect that leads nowhere fails the app's verification, so Frontport creates its folder when it installs, updates, rolls back or re-signs, right after Delete Data (after the primer, so Data is there again at once), after restoring a Snapshot, and before each launch it makes, making Data first if it's gone. As in Seeding, it never follows a link there: the Port can plant one anywhere in its Data. Each folder is opened, no-follow, from the one before, so a link, or anything but a folder, on the way to `Data/<to>` or at it is refused, never followed or opened. The Packager walks to them once more right before codesign verifies, since codesign opens each (a FIFO there would hang it), and stops codesign after 10 minutes.
- **The link rule gets a second exception.** Besides the link to the Build Assets ([ADR 0004](0004-keep-build-assets-outside-the-app.md)), the Packager's checks let through a Redirect's link only with exactly the text it gives one: absolute and canonical, the canonical containers folder, then `<bundleId>/Data/<to>`, with no empty, `.` or `..` component in `to`; never another Port's Data. When packaging, only the links it has just placed pass. Every other link is followed from inside the app one component at a time, each link on the way read and expanded from its own folder, as `openat2`'s `RESOLVE_BENEATH` would, and refused when any text on the way is absolute, when `..` climbs above the app, when the way is or passes through one of the Packager's links, or after 40 links; it must also resolve inside the app. So upstream can't ship a link that passes as a Redirect, nor one that reaches the Port's Data through a Redirect or by climbing out through other links and bounces back into the app through a link the Port left there. That matters most for a Port with only the Build Assets link, as Starship and zelda3 have: it's verified with `--strict=sideband`, so this check is all that stands in the way. Re-signing finds the Packager's links in the app, not from the Catalog, and checks each still has its shape.
- **They stay clear of code.** A Redirect's `path` is inside `Contents/Resources/`, and neither it nor `buildAssets.path` may sit at, above or inside a code location (`MacOS`, `Frameworks`, `PlugIns`, `XPCServices`, `Helpers`, `Library/LoginItems`), `_CodeSignature`, `Info.plist`, `CodeResources` or `PkgInfo`, of the app or of an app nested in it. A link there would let the Port swap in, through its Data, a program that macOS starts outside the sandbox: with `Contents/MacOS` linked into Data, the app signs and verifies, and the Port could then replace its executable with one that isn't sandboxed. Every component of a Redirect's `path` and `to` and of `buildAssets.path` is plain ASCII (letters, digits, spaces, `.`, `_` and `-`): APFS folds case and Unicode, so `Contentſ` names `Contents` there, and only between plain names is comparing without case enough.
- **The Catalog declares them.** Each is reviewed with its entry, and the lint keeps `path` inside `Contents/Resources/`, clear of code, `buildAssets.path` and the other Redirects, and `to` inside Data. The Packager checks the same again.
- **Folders only.** A Redirect leads one folder into Data, so a file a Port writes beside its executable stays unwritable. OpenGOAL's `gk` also writes `data/imgui.ini` in the bundle; that write fails silently, and the game runs without keeping ImGui's window layout.
- **Prebuilt Ports can use them too.** The Packager links Redirects in any app, so a prebuilt Port that writes beside its executable needs no Recipe.
