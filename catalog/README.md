# Catalog

Frontport's own Catalog: the curated list of Ports Frontport offers, signed with Ed25519. Frontport fetches it from this folder on `main` (`https://raw.githubusercontent.com/svich/frontport/main/catalog/`) and ships a copy in `App/Resources/catalog/` for first launch. Other Catalogs, which the user adds in Settings, follow the same format, each signed with its own key ([Adding a Catalog](#adding-a-catalog)).

| File | What it is |
|---|---|
| `catalog.json` | The `CatalogDocument` (FrontportKit/Sources/FrontportCore/Catalog.swift), schema version 4: version 2 lets a ROM name a Platform instead of a Game, version 3 adds the `sourceport` Kind, and version 4 each Platform's `medium` and a ROM's `type`, `update` or `dlc`. A Game's optional `base`, and a folder ROM's optional `configs` and `steam`, added since, need no new version: Frontports that don't know them ignore them, and just don't match a played Steam folder |
| `catalog.json.sig` | Base64 Ed25519 signature over the exact bytes of `catalog.json`, then a newline |
| `recipes/*.sh` | Recipes for source-built Ports, and unpack Recipes for installers. Each is pinned by a `recipeSHA256` in `catalog.json`, so the signature covers it |
| `dev.key` | The development private key. Gitignored (`catalog/*.key`), never committed |

## Changing the Catalog

Every change to `catalog.json` or a Recipe needs a new signature and a new bundled copy. The tests fail if the signature doesn't verify with the key built into Frontport, or if `App/Resources/catalog/` differs from this folder.

```sh
cd FrontportKit
swift run frontport-catalog sign --key ../catalog/dev.key --update-recipe-hashes ../catalog/catalog.json
swift run frontport-catalog verify ../catalog/catalog.json
swift run frontport-catalog bundle ../catalog ../App/Resources/catalog
```

- **Sign:** decodes the document, checks it for dangling references, unused ROMs, malformed ids, bundle IDs, hashes or paths, duplicate code-signing exceptions and Ports of one Project that disagree, and checks each Recipe's SHA-256. `--update-recipe-hashes` rewrites the `recipeSHA256` values in place instead of failing on a mismatch.
- **No emulators:** a Port runs its Game as native Mac code, of one of the four Kinds. Emulators (DOSBox, RetroArch) and compatibility layers (Wine, CrossOver) that run the Game's original binaries don't go in the Catalog.
- **Bump `issued`:** Frontport never replaces its cached Catalog with one whose `issued` is older.
- **Ids:** lowercase letters, digits and hyphens, starting with a letter or digit, because an id names the Port's folders. Not starting with `unpack-`, which names the unpack Recipes' build folders.
- **Keep `bundleId`:** always `dev.frontport.port.<id>`. It ties a Port to its Data, so it never changes.
- **Give a Steam folder ROM its `steam` and `configs`:** `steam` is the app id and, when the ROM is a folder inside the install folder, that folder. `configs` are the files Steam's depot manifests flag as user config (flag 1) under it, relative to it; leave out versioned user config (flag 2). Compute the hash from the manifests without them ([ADR 0014](../docs/adr/0014-add-steam-games-by-their-manifests.md)).
- **List every ROM in a Requirement:** Frontport accepts only ROMs a Requirement lists, so a ROM in `roms` that none lists is an error.
- **Date a new Port:** set its `firstRelease` to when upstream first published it (see [First Releases](#first-releases)). New Ports orders Ports by it.
- **Give each Game its Genres:** from `genres`, main one first. A Genre no Game names is an error.
- **Keep a Project's Ports alike:** Ports with the same `releases.repo` are one Project, which follows one set of Releases. Give them the same `name`, `developer`, `kind`, `source` and `website`: the Project page takes these from its first Port, and signing fails otherwise.

## Adding a Catalog

Anyone can publish a Catalog for Frontport ([ADR 0012](../docs/adr/0012-add-catalogs-by-link.md)): a folder served over https with `catalog.json`, `catalog.json.sig`, its Recipes and `catalog.pub`, the public key, base64 on one line. The user pastes the folder's URL into Settings › Catalogs › Add…, or opens a `frontport://add-catalog?url=<folder>&key=<public key>` link from a web page. GitHub drops such links from READMEs, so a repository's README shows the URL to paste.

```sh
cd FrontportKit
swift run frontport-catalog keygen /path/to/other.key > /path/to/catalog/catalog.pub
swift run frontport-catalog sign --key /path/to/other.key --update-recipe-hashes /path/to/catalog/catalog.json
swift run frontport-catalog verify --public-key "$(cat /path/to/catalog/catalog.pub)" /path/to/catalog/catalog.json
```

- **Name it:** `name` at the top of `catalog.json` is what Settings and the store page call the Catalog.
- **Make it whole:** it lists the Platforms, Genres and Games its Ports use, even ones Frontport's Catalog lists too, and passes the same checks when signed. Frontport refuses a Catalog that doesn't.
- **Keep ids its own:** Frontport's Catalog, and then Catalogs added earlier, keep an id that two Catalogs list. A Port installed from one Catalog never takes updates from another.

## Keys

Frontport trusts exactly one public key, `CatalogSignature.builtInPublicKeyBase64` in `FrontportKit/Sources/FrontportCatalog/CatalogSignature.swift`. It is currently the **development key**, whose private half is `catalog/dev.key` on the machine that generated it. A Catalog signed with it is fine for development builds only.

To switch to a release key:
1. Generate it offline with `frontport-catalog keygen release.key`. Keep the private key out of the repository, for example in a password manager or a CI secret.
2. Put the printed public key into `builtInPublicKeyBase64`, replacing the development key.
3. Re-sign `catalog.json` with the release key, bundle it, and commit both.
4. Ship a Frontport update. Rotating the key always takes an app update, because older builds only trust the key they were built with.

A lost development key costs nothing: generate a new one with `keygen catalog/dev.key`, embed it, and re-sign.

Tests never need either key. The synthetic end-to-end test (`SyntheticEndToEndTests` in `FrontportKit/Tests/FrontportIntegrationTests`) generates a key pair, signs a test Catalog with it and serves it from a local server, so `refresh()`, signature checks and Recipe fetches run over real HTTP.

### Choices made

- **Channels:** every Port offers only `stable`. None of them publishes prereleases or nightlies as GitHub Releases.
- **`strip`:** paths inside the app, relative to the bundle and under `Contents/`, that Frontport deletes before signing. Used for upstream pieces that would act outside the sandbox's promise, such as sm64coopdx's self-updater (checked in v1.5.1's `sm64coopdx_macOS_ARM.zip`).
- **`launch.environment.SHIP_HOME`:** 2Ship and Ghostship set `SHIP_HOME` through `LSEnvironment` in their Info.plist. LaunchServices applies that only to launches through it, so the Catalog sets the same value for launches by Frontport's Launcher.
- **OpenGOAL:** one Port per game, `opengoal-jak1`, `opengoal-jak2` and `opengoal-jak3`, because a Port has one Game, one container and one way to launch. `opengoal.sh` builds each, taking the game from the Port id. Each shows its Game's artwork: SteamGridDB's OpenGOAL entry is one for every game. Jak 3 is offered as the beta the OpenGOAL Launcher offers, though jak-project's README still says it has work left.
- **`redirects`:** links the Packager puts at paths inside the app, under `Contents/Resources/` and clear of its code, in plain ASCII, leading to folders in the Port's Data, for a Port that writes beside its executable. The OpenGOAL Ports redirect `data/log`, where `gk` writes its logs, rather than patch `gk`; Frontport creates the folders without following links.
- **Permissions:** network is on only for Ghostship (its mod service at launch) and sm64coopdx (online play). UZDoom's multiplayer is optional and off by default.
- **Xash3D FWGS:** one Port per Game, `xash3d-half-life`, `xash3d-opposing-force` and `xash3d-blue-shift`, like OpenGOAL, from one Recipe that takes the hlsdk-portable branch from the Port id. Its Kind is Recreation: the engine reimplements GoldSrc without its code, though the game code is Valve's released SDK. Its Games are on the Windows Platform, like Gothic II. Opposing Force and Blue Shift have Half-Life as their Base, so their Ports take its `valve` folder too. `stable` pins a commit, since upstream publishes no versioned Releases. Each shows its Game's artwork. Played Steam folders, with saves and changed configs, don't match and can be kept Unverified ([ADR 0011](../docs/adr/0011-keep-unlisted-files-unverified.md)). The HD packs (`valve_hd`, `gearbox_hd`, `bshift_hd`) are left out.
- **UZDoom:** one Port per Game, `uzdoom-doom`, `uzdoom-doom2`, `uzdoom-heretic` and `uzdoom-hexen`, like OpenGOAL, each Seeding its IWAD under the name UZDoom looks for and launching it with `-iwad`. Their Kind is Sourceport: UZDoom descends from the Doom source id Software released, not from a decompilation. Each shows its Game's artwork: SteamGridDB's UZDoom entry is one for every game. `stable` follows full Releases; the rolling `x-preview` prerelease is left out.
- **dethrace:** a source build though upstream publishes a Mac app, because that app expects SDL installed separately. One Port per Game, `dethrace` and `dethrace-splat-pack`, as for OpenGOAL: dethrace tells them apart by their files, so the Recipe is the same. It plays the Game from a folder of files, a folder ROM ([ADR 0007](../docs/adr/0007-take-a-pc-game-as-a-folder.md)), which Seeding fills into its own folder in the Port's Data without replacing what dethrace wrote there. Carmageddon accepts GOG's Max Pack before the freeware demo of April 1997, so anyone can try it; a user who adds the Max Pack after playing the demo gets a fresh folder, and the demo's is renamed. Both Ports show their Game's artwork: SteamGridDB has no dethrace entry. It launches full screen, as upstream does; `Windowed = 1` in `dethrace.ini` beside the game's files changes that. The demo has only the 320×200 graphics, so `Hires = 1` crashes it.
- **Fallout CE:** a source build at a pinned commit, though upstream publishes a Mac app, because that app plays from the folder it sits in. The Recipe makes it play from its own folder in its container, where Seeding fills in the game's folder ([ADR 0007](../docs/adr/0007-take-a-pc-game-as-a-folder.md)) and Fallout writes its settings and saves among the game's files. The Catalog takes the CD itself as the folder: as the disc's folder, or its image, a `.iso` that `iso.sh` unpacks like an installer ([ADR 0008](../docs/adr/0008-unpack-installers-in-the-build-sandbox.md)). The CD's other files, DirectX and the manual, come along, since a folder ROM is all its files; Seeding clones them, so they take no space. It shows its Game's artwork: SteamGridDB has no Fallout CE entry.
- **Installers:** GOG sells PC Games as Windows installers, which a Mac can't run. The Catalog lists one by its hash with the unpack Recipe that turns it into the folder ROMs it yields ([ADR 0008](../docs/adr/0008-unpack-installers-in-the-build-sandbox.md)), so a user adds the file GOG gave them. A PC Game's CD image is one too: `iso.sh` unpacks it with the bsdtar macOS ships, so it builds nothing. `innoextract.sh` pins an innoextract commit after its last Release (1.9, 2020), which needs patches for current Boost and CMake, as Homebrew applies, and lacks later fixes for GOG Galaxy installers.
- **OpenGothic:** a source build of upstream's latest tag, because its Releases are prereleases holding a bare executable. The Recipe wraps it in an app with upstream's icon, and builds `glslangValidator`, which compiles its shaders to SPIR-V, from a pinned glslang instead of Homebrew; Tempest, its engine, makes Metal shaders from them at run time. Its Game is on a new Platform, Windows, since Gothic II never ran on DOS. It takes the folder of an installed copy, which ADR 0007 identifies by all its files, so only a copy that hasn't been started matches. Controllers are off: Tempest reads no game controllers. It shows its Game's artwork: SteamGridDB has no OpenGothic entry.
- **OpenSupaplex:** a source build of upstream's latest tag, though upstream publishes a Mac app, because that app's frameworks no longer sign. Upstream's own Apple file layer already reads the game's files from the bundle and writes into Application Support, so nothing is patched. Supaplex's files are freeware and come with it, so it is the first Port that needs no ROM. Its Kind is Decomp: it is written from the disassembled game. Supaplex is on the MS-DOS Platform and in a new Genre, Puzzle. It shows its Game's artwork, SteamGridDB's only Supaplex entry, the 2018 Steam release.
- **Code-signing exceptions** mirror the upstream app's own entitlements. Four upstream apps aren't signed with the hardened runtime at all: 2Ship, Ghostship, sm64coopdx and OpenGOAL. OpenGOAL needs an exception under it anyway: `gk` maps the game's memory a second time as executable (`mach_vm_remap`) and runs code written through the first mapping, which the runtime kills without `allow-unsigned-executable-memory`. `allow-jit` doesn't cover it, because the memory isn't `MAP_JIT`. UZDoom is signed with the hardened runtime and no entitlements, so it needs none.
